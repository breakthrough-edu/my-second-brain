# Distill Mode: the weekly maintenance ritual (tidy + distill)

About 10 minutes of the owner's attention: the AI does the hygiene, then brings distillation proposals; the owner only rules. This mode is the engine; the reminder doorbell lives in the generated command-base skill (morning check against `99_Meta/maintenance-state.md`), and any mode entry backstops it. Cadence comes from `cadence_days` in that same file (weekly by default); every staleness comparison in this mode reads that key rather than assuming 7.

Two halves, always in this order (clean room first, then think):

## Half 1: Tidy (structure hygiene)

**Run the machine pass first.** Before the human scan, run the read-only linter: `python3 <skill>/scripts/checkup.py "<vault-path>"`. It covers the mechanical half of the checks below in seconds, so the human scan spends its attention on judgment (orphans, misfiling, distillation). The script is strictly report-only: it never moves, renames, or deletes anything, and its findings are proposals, not actions. Fold its output into the ONE report below; the owner still rules on every fix.

⛔ **One finding is not foldable: a `house-vintage` ERROR.** It means the generation of this house is not settled as the current one (four ways: a recorded version older than this skill's, one newer than it, the two records disagreeing, or folder shapes from an earlier generation or from two at once). Whichever way, the shapes every check below tests for may not be the shapes this vault has, and a tidy that "corrects" them would be moving the owner's real content toward a house they do not live in. Stop the tidy there, report the mismatch as `SKILL.md`'s house-vintage gate (mode routing, step 1) describes, and propose no moves.

⛔ **And the stop reaches Half 2, which may still read and still propose, but ⛔ nothing lands.** Every path in this file that writes is written for the current shape, so each one is a structural write into a house that may not have that room. The three that read as compulsory are named here, because "nothing lands" is a general sentence and a specific instruction two screens down wins every argument with one:

- **Pipe 5, step 1** moves a superseded harvest report into `98_Archive/` and says carrying its proposals across **is not optional**. ⛔ On a house that has no `98_Archive/`, doing it creates one, which is the two-shapes accident happening inside the very pass that was supposed to prevent it. Leave the old report where it is, `status:` untouched, and tell the owner why it is being left.
- **Pipe 2** files the weekly rollup in `02_Command-Base/Reviews/` and says it **needs no ruling** beyond a glance. That "no ruling" assumes the folder exists. Write the rollup into the chat, name the folder it would have gone to, and let the owner place it.
- **Pipe 5, step 4** writes a `cb: decision` into `02_Command-Base/Decisions/`, and a decision candidate is exactly the thing an owner will say yes to quickly. Their yes is to the content, not to the address; show the note and let them file it.

The same holds for the obvious one: an approved lesson or playbook into `04_Methodology/` is a structural write into a vault whose methodology layer may sit elsewhere under another name. In every case, show the owner the text and let them place it themselves. ⚠️ The line between what is still allowed and what is not: `filing-log.md` and `maintenance-state.md` updates are state, they exist in both generations, and they stay legal, so record that the pass ran and what it found. Moving a file into `98_Archive/` is not state, and neither is anything that creates a folder.

Scan the vault and build ONE report. Do not fix anything yet. The seven checks:

1. **Orphans:** notes carrying no inbound links and reachable from no door (skip `99_Meta`, `98_Archive`, daily notes). Remember what "reachable" means here: entity notes are found by type plus address, not by links (doctrine §3), so a client note with no backlinks is normal. The real orphan is a note whose type family has no home rule, or a file sitting in a folder nothing explains.
2. **Misfiled:** notes whose content contradicts their location (a procedure sitting in an entity room; a client note in Inbox; a filled record where a template should be; a project in the wrong lane by the §1 ladder). Judge by the doctrine's filing tests and precedent table; cite the rule per item.
3. **Inbox drain:** everything still sitting in `00_Inbox/` when maintenance runs gets named, each with a proposed destination (doctrine-cited). There is no age threshold to compute: whoever runs the pass names what is there.
4. **Doors and the directory:** every folder that should have a door has exactly one `_`-prefixed file, and no folder has two (§5). `Home.md` is audited against the filesystem in both directions: every folder that exists is listed, every path listed exists. Cross-reference `capture-progress.md`: rooms or lanes captured once and untouched for four cadence periods are listed as cold, proposal only (revisit, or mark stable).
5. **Schema violations:** every note checked against its family in doctrine §8, which is the only place the shapes are written: missing required keys, values outside a closed list, mis-cased enums, off-vocabulary tags. A key §8 has NOT declared is not a violation: flag it as a judgment call ("register it in §8, or drop it"), never as an error. Watch `lane:` in particular: it is required on SOPs, playbooks and lessons, and a blank one makes that note invisible to every lane-filtered view.
6. **Memory weight:** keep `99_Meta/memory.md` lean. Session-log entries older than 30 days rotate to `99_Meta/memory-archive/YYYY-MM.md` (create the folder on first rotation; append under a dated heading, never delete). Recent decisions trimmed to the newest 10 (the full notes live in `02_Command-Base/Decisions/`). Active-initiatives rows matching no live work get flagged. Watch-for entries sighted 3+ times get proposed for promotion into `99_Meta/profile.md` (only if that file exists). Rotation and trimming are mechanical; promotions and flags need the owner.
7. **Filing patterns:** read `filing-log.md` since the last tidy. Three or more filings to the same destination that has no room yet → propose the room. Repeated filings decided by judgment with no rule to cite → propose a new row for the precedent table in doctrine §2 (on approval: append the row, add a revision-log line). Report only; nothing structural gets created without the owner.

Present the report compactly, grouped by check, each item one line: what, where, proposed action, rule cited. Then ask for one ruling: fix all, fix by group, or walk through item by item. Purely mechanical items (a stale `updated:`, a dead link, a Home entry that lost its folder) can be pre-marked "will do unless you object". Moving or renaming anything the owner wrote needs explicit approval, always, and a move must rewrite its inbound links in the same breath (§3).

Execute what was approved. Append every move to `filing-log.md`. Set `last_tidy:` in `maintenance-state.md` and append a one-line history entry (date, items found, items fixed).

## Half 2: Distill (the distillation pipes)

Now the thinking half. Read the week's material and bring PROPOSALS. The discipline, stated to the owner once per run: **distillation proposes, judgment rules.** Nothing enters `04_Methodology` unless the owner says yes; that is what keeps the layer honest (it holds judgment, not sediment).

**Pipe 1, decisions → playbooks.** Read `02_Command-Base/Decisions/` for this business (domain filter), recent 10 to 20, and remember what they already are: the set of ACTIVE decisions IS the rulebook (§7), so a repeated call does not need to be "promoted" anywhere to have force. What is worth proposing is the layer above: when the same trade-off has been resolved the same way three or more times, the reasoning behind it is a piece of methodology. "Five of your last eight supplier decisions chose delivery reliability over unit price. That is a way of deciding, not just eight decisions. Worth writing as a playbook?" On yes: one note in `04_Methodology/Playbooks/`, listing the evidencing decisions as links, `lane:` set, `confirmed_by_owner: true`.

Also worth surfacing here: an active decision that contradicts another active decision, and an event decision (hire this person, buy that oven) that was executed but never flipped to `closed`. Both are one-line fixes that keep the active set a rulebook instead of a junk drawer.

**Pipe 2, the week's rollup.** Compress the week's `01_Daily/` entries into a short weekly rollup, filed in `02_Command-Base/Reviews/` (`type: weekly-review`). Refresh `## Current state` in the wing's `_<Business>-Guide.md` if the week moved it. This pipe needs no ruling beyond a glance; it is memory maintenance, and it is what keeps the wing guide a truthful one-pager for every future session.

**Pipe 3, learning and potholes → lessons.** Read new material in `02_Command-Base/Resources/` plus anything tagged `#lesson-candidate` this week. Where something was actually APPLIED or actually hurt, propose a Lesson: "You clipped that pricing article Tuesday, and Thursday you repriced the bundle. Worth a Lesson note that fuses the two?" Study lands in Resources, realization lands in Methodology, and the difference is the owner saying "yes, that is now how I operate." On yes: a note in `04_Methodology/Lessons/` from the Lesson template, `lane:` set, `confirmed_by_owner: true`.

⛔ **Types do not transmute.** A playbook never "demotes" into an SOP and a lesson never becomes a decision. What travels is content, not the note: pits become lessons; recurring lessons and clustered decisions distill upward into playbooks; playbooks and lessons inform the next SOP someone writes (§7). Say it when the loop is visible, but never move a note across families to say it.

**Pipe 4, the lab scan.** One pass, all labs, and it runs in both directions (doctrine §9).

- **Opening.** Look at the playbooks that are actually being used and run the §9.5 gate against `99_Meta/lab-gate-config.md`, carrying its NO-prior: the line is alive (new outputs in the window) AND judgment is accruing (related lessons or decisions) AND an external, countable feedback signal exists. All three, or no proposal. Busy with no judgment wants a better SOP, not a lab; activity with no outside signal can only measure self-satisfaction. When all three open, propose candidacy in one sentence and stop there: the `playbook-lab` skill runs the actual opening, interviews the rubric into existence, and seeds the register and thresholds. ⛔ Never hand-build a lab's organs from this pass.
- **Running labs.** For each open lab, read its register against its thresholds. A bet whose verdict condition is met, or a threshold that has fired, becomes one proposal to revise that lab's playbook. The owner rules; the playbook is the single authority, so nothing downstream needs updating afterwards.
- **Closing.** Two propose-only signals: silence (no output past the config's silence window) and idling (outputs continue but scores stop, bets never resolve, proposals never land). Ask "recommit?" once, then propose closing, and state the guarantee: closing archives the organs and a scoreboard snapshot to `98_Archive/`, and the playbook text keeps every criterion it earned. Learning is archived, never destroyed.

If the `playbook-lab` skill is not installed, still run the scan and still say what it found; record the accepted proposal and note that opening or closing is pending that skill. A scan is cheap and its findings keep.

**Pipe 5, the session harvest (only when session memory is installed).** Read `session_memory_installed:` from `99_Meta/bootstrap-progress.md`; unless it says `installed`, skip this pipe silently, nothing else depends on it. Session memory (setup step 6.9) keeps a searchable index of every Claude Code conversation on the machine; this pipe is the weekly pass that turns the not-yet-reviewed ones into proposed memories. Same law as every pipe, worth saying to the owner in these words once: the AI reads, the AI proposes, nothing is kept until you tick it.

⛔ **This pipe carries its own house-vintage gate, and it is the only pipe that needs one.** Every other structural writer in this product is reached through mode routing, which settles the vintage before anything runs. This one is not: the generated command-base skill's maintenance doorbell calls Pipe 5 by name, on a timer, **without asking**, and lands here without Half 1 having run. So run the check here, at the top, every time: `python3 "<skill>/scripts/checkup.py" "<vault>"` and read its `House vintage` line and any `[house-vintage]` finding.

- **Current, or the check cannot judge:** carry on, all five steps as written. ⚠️ One exception inside "cannot judge": if the reason is that `99_Meta/structure-doctrine.md` is missing, this vault has no constitution to be current with. ⛔ Treat that as "anything else" below and say so, rather than reading a silence as a pass.
- **Anything else** (an older recorded version, a newer one, the two records disagreeing, or an unmarked house whose shape reads as an earlier generation): ⛔ **the gate blocks addresses, not work.** Block exactly the writes that use an address this generation introduced, and complete everything else as written, because a pass that quietly does less than it says is its own kind of damage.
  - **Steps 2, 3 and 5 run untouched.** They write to the tool's own state directory, to `00_Inbox/`, and to `99_Meta/maintenance-state.md`, and all three exist in every generation.
  - ⛔ **Step 1 does not move the superseded report** (`98_Archive/` is this generation's address). Leave it where it is, and still carry its unanswered proposals into the new note, which is the part of step 1 that actually matters. Its `status:` may still flip to `superseded-<date>` in place: that is the file's own frontmatter, not a new address.
  - ⛔ **Step 4 blocks two of its three destinations, not the step.** A decision note (`02_Command-Base/Decisions/`, `lane:`) and a distilled note routed into `04_Methodology/` both use new addresses, so hand those to the owner in chat instead: "your vault is an earlier generation, so I am not filing this; here is where it would go in yours." **An accepted memory or profile line still gets written.** `99_Meta/memory.md` and `99_Meta/profile.md` sit in the same place in both generations, and an owner who ticked a proposal has said yes to it. ⛔ Never let a tick land nowhere and go unmentioned.
  - **A report that already carries ticks still gets finished and closed.** Step 1 sends it to step 4, and step 4 above is open for exactly this. Those ticks are the owner's intent from a previous week; if the blocked destinations mean it cannot fully close, say which items are waiting on the vault's generation, so it stops resurfacing as a silent unfinished thing every week.
  - Say once, plainly, that this is why.
- ⭐ **This gate is deliberately not an offer.** The doorbell exists precisely for the owner who never answers offers, so an offer here would be answered by nobody and the write would happen anyway.

1. **A pending report never blocks a new pass.** Look in `00_Inbox/` for a file whose frontmatter says `type: harvest-report` and `status: inbox-unprocessed`. If one exists **and carries ticks** (`- [x]`), finish that one first: those ticks are the owner's intent and no later report will carry them. If it exists **untouched**, supersede it: **copy its unanswered proposals into the note you are about to write**, then set its `status:` to `superseded-<date>` and move it to `98_Archive/`, and run a fresh pass anyway. Carrying them across is not optional and it is not the same as re-mining them: on the automatic weekly path the bookmark was already committed when that note was written, so those conversations will never surface again on their own. The proposals are already drafted, so moving them forward costs nothing; dropping them would quietly throw away a week the owner simply did not get around to answering. An ignored report must never become a permanent stop either: one skipped week used to switch this pipe off for good and turn the doorbell into a daily nag.
2. Otherwise run the tool (it ships in this skill's payload at `scripts/session-history/`; resolve the running skill's folder the same way setup does): `python3 "<tool>/sh" ingest` to refresh the index, then `python3 "<tool>/sh" harvest`. What lands is a **draft in the tool's own state directory** (`~/.my-second-brain/<date>-harvest-draft.md`), never the vault. It is cue-word matching with nothing judged, and it is addressed to you, not to the owner.
3. **You do the reading. The draft is your worklist, not theirs.** This is the whole job, and skipping it is the documented failure mode: two passes that reached the owner raw were adopted at 0 of 649 and 0 of 26, while the one pass that went through a real read first was adopted 8 of 8. Open the sessions behind the leads worth opening (`python3 "<tool>/sh" show <session-id>`), including any subagent transcripts that session spawned, because that is where a third of the good material lives and the draft's own selection cannot see it. Drop anything already covered by `99_Meta/memory.md`, `99_Meta/profile.md`, the doctrine, or an existing note. Then write the owner's note into `00_Inbox/`, and that note is the deliverable:
   - Frontmatter `type: harvest-report`, `status: inbox-unprocessed`, and the draft's `sessions:` list **copied verbatim**. That list is the contract `harvest commit` reads back; the prose above it is yours to write freely.
   - **At most 3 to 5 proposals**, each one already written: type, a name, one line of what it is, one line of why it matters, and the body drafted well enough that "yes" is the only action left. A pointer to the source session goes on every single one, so the owner can always ask "how do you know that" and so a bad entry can be traced and pulled later.
   - **The admission test is not "is this interesting" but "if this is not in the default context, will the AI get something wrong next week."** Facts the owner can look up do not qualify; `search` already covers those. Preferences, judgments, and traps that will bite twice do.
   - **Propose retirements too.** Read `99_Meta/memory.md` with the same eyes and name anything that has gone stale ("this says the launch is blocked on X, which shipped three weeks ago, drop it?"). A pipe that only ever adds is how a memory file turns into a pile of mixed-vintage claims that quietly make the AI worse, and the owner is the only one who knows which true sentences have expired. Past roughly 120 lines, aim for one out per one in.
   - An honest zero is the normal outcome on a quiet week. Say one line, commit the draft anyway (those conversations are reviewed now), and move on. Never pad to look productive.
4. On the owner's ticks, write each keeper where it lives: a **memory** candidate is appended to `99_Meta/memory.md` (a durable fact about the owner themselves belongs in `99_Meta/profile.md` when that file exists); a **decision** candidate becomes a `cb: decision` note in `02_Command-Base/Decisions/` with `domain:` and `lane:` filled; a **note** candidate routes exactly like Pipe 3 material. Nothing is ever written into `99_Meta/memory.md` or `99_Meta/profile.md` without the owner having seen the exact words first: those two files enter every future session's context, a wrong line there never errors, it just steers, and it also becomes next week's harvest input.
5. Close the loop: `python3 "<tool>/sh" harvest commit "<the Inbox note>"` (the only step that marks those conversations reviewed), flip that note's `status:` to `processed-<date>`, delete the draft from the state directory, and set `last_harvest:` in `maintenance-state.md`.

If the tool errors or is missing despite the flag (a moved install, a new machine), say so plainly, skip the pipe, and never let it block the rest of the distill.

## Close

- Set `last_distill:` in `maintenance-state.md`, append the history line (proposals made / accepted).
- Check the vault root `CLAUDE.md` against reality (a skill renamed, a second wing added, language changed, a rule amended). If it has drifted, propose the specific edit; the owner approves; never rewrite it silently.
- If this was the first time `04_Methodology` received ANY content, mark the moment; one line, no ceremony: "Your fourth layer is no longer empty. That is the layer capture could never fill."
- Surface next week's hook once, reading `next_suggestion:` from `capture-progress.md` so the hook is concrete: "Doorbell rings in <cadence_days> days. <Next room or lane> is the suggested next move-in. Anything you want me to watch for between now and then?"

## First-run honesty

If maintenance runs before there is anything to distill (thin journal, no decisions yet), say so and run tidy only. Never manufacture insight from insufficient material; a short honest run builds more trust than a padded one.

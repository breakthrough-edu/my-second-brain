# Scaffold Spec: the fully wired vault (tree v6)

This is the exact structure Setup mode creates. The principle is **full wiring**: not bare folders but every door file pre-built, every frontmatter shape already legal under the doctrine, every template in place. The AI always has a firm anchor to file against; the owner never faces a blank page. Keep every generated file light: a door sign, a filing test, an Observations section. No tutorials inside doors, and no inventories anywhere: **Home.md is the only directory this vault has** (doctrine §3), and a second list is a second thing to keep true.

All `mkdir` operations use `mkdir -p` (idempotent). **Never overwrite an existing file** during scaffold; skip and report instead.

Replace `{{BUSINESS}}` with the business folder name (English, hyphenated, e.g. `Aroma-Coffee`), `{{BUSINESS_NAME}}` with the display name, `{{BUSINESS_TAG}}` with the domain tag (kebab-case, e.g. `aroma-coffee`), `{{DATE}}` with today. **Scope exception:** inside the files written to `99_Meta/Templates/`, keep `{{DATE}}` literal; those are starter shapes for future notes and the date is filled when each note is created.

**The law this file builds.** Everything below is the physical form of `templates/structure-doctrine.template.md`. Where the two ever disagree, the doctrine wins and this file is the bug. Section references in this document point at that file.

**Doors, and only one per folder.** Every folder that needs explaining carries exactly one `_`-prefixed file (§5): a `_<Name>-Guide.md` for rooms, lanes, brand subfolders and wings; `_SOP-Menu.md` for `03_SOP/`. Two rules follow, and the wiring check enforces both:

- **The four layer folders get no door.** `01_Assets/`, `02_Work/`, `03_SOP/` (beyond its menu) and `04_Methodology/` are containers of rooms, not rooms. `guide_family` is a closed list (`wing / room / lane / brand / lab`, §8) and a layer is none of them, so a layer guide could not carry a legal value. The wing guide explains the four layers in one place; Home lists them.
- **`04_Methodology/` ships with zero `.md` files**, guides included. Capture cannot write there and nothing lands without the owner's yes (§4, law 4); an empty layer with a welcome sign is not empty.
- ⭐ **`Playbooks/` holds methods and playbooks side by side, flat, and that is deliberate.** A method is named `<the-work>-method.md`, a playbook `<the-kind-of-work>-playbook.md`, and a playbook that earns a lab becomes a folder in place (§9). ⛔ **No `Methods/` folder is scaffolded and none should be added:** one address is what lets the owner see all three degrees of maturity at once, and a method that gets distilled into a playbook then never has to move.

## Preset toggles

Two yes/no questions at setup, recorded in `bootstrap-progress.md`:

1. **Physical outlets?** (shopfront, branches) → `01_Assets/Outlets/`
2. **Machines or equipment?** → `01_Assets/Equipment/`

Untoggled rooms are simply not created. Either can be proposed later during capture when the business turns out to need one (propose, owner approves, create). There is no third toggle any more: the old importing toggle only ever created SOP subfolders, and `03_SOP/` now ships empty and flat (§1).

## The personal wing is not a question

`03_Personal-Wing/` and its six life rooms are always created, no question asked. The doctrine states the wing's contents flatly (`Personal-Projects/` plus exactly six rooms, "Nothing else"), so a vault missing them is a vault that does not match its own law. There is no `personal_wing_preopened:` flag any more.

## File skeletons

⭐ **This section names which files scaffold writes and what goes in their blanks. It does not carry their shapes.** Every shape that a `99_Meta/Templates/` file owns is written once, in [templates/note-templates.md](../templates/note-templates.md), and scaffold copies it from there. The reason is the whole point of shipping templates at all: the door a vault gets tonight and the door a session writes six months from now have to come out of one source, and a second copy here is exactly the artifact that drifts, silently, in the direction of whoever edited last. ⛔ **Never paste a shape back into this file to "make it easier to read".** Two other kinds of file appear below and neither is an exception to that. Some carry their own dedicated template and this file only points at it (`Business-Profile.md`, the doctrine, the tag vocabulary, `memory.md`, `lab-gate-config.md`, `CLAUDE.md`). The rest are written out here in full because nothing else owns them: `Home.md` and the `99_Meta` state files are singletons that setup writes once and no session ever writes again, so there is no template for them to drift from.

### The guide file (`_<Name>-Guide.md`, every room, lane, brand subfolder and wing)

**Shape: the `Guide.md` block in [templates/note-templates.md](../templates/note-templates.md).** Copy it, including its bottom comment block, into `99_Meta/Templates/Guide.md`, and write every door in the vault from it.

What scaffold fills in, per door:

- `guide_family`: `wing` for the two wing doors, `lane` for the four lanes of `02_Work/`, `brand` for the three subfolders of `<Brand>-Brand-Assets/` (§8's own comment defines the value as "a subfolder of `<Brand>-Brand-Assets/`", so `Products-Services/` carries it too), `room` for every other room including the `<Brand>-Brand-Assets/` folder itself (doctrine §1 lists it among the entity rooms of `01_Assets/`, so it is a room that holds rooms). (`lab` is the fifth legal value and scaffold never writes it: labs are born later, by the `playbook-lab` skill.)
- The door-sign line and the **Files here when** test: ⛔ **never written here and never improvised.** Every door scaffold builds has both lines waiting for it in one of two files, and setup copies them: [work-lanes.md](work-lanes.md) ("The four doors" section) for the four lanes; [rooms-assets.md](rooms-assets.md) for everything else, business rooms in its body, and the personal wing's eight doors plus `Resources/` in its last two sections. Copy, do not paraphrase, so the door and the reference always say the same thing. On a `中文` install translate the two lines at write time; file names stay English.
  ⭐ **If a door ever has no source there, that is the bug, and the fix is to write the two lines into the reference first.** Improvising one at install time is the failure this rule exists to stop: a door file is read every time anyone works in that folder, so two installs that each invent their own door signs are two different products, and nothing anywhere would ever report it.
- `## Observations` ships present and empty. It is where sessions write what they notice about the folder; an empty section is the invitation.

⛔ **No Inventory section and no Navigation section.** A guide is not a directory (§3); Home is. ⛔ **No project list in a lane guide**: the lane's job is to be the anchor a journal line can link when work has no project, not a second copy of what the folder already shows.

### `04_{{BUSINESS}}-Business-Wing/_{{BUSINESS}}-Guide.md` (the wing door)

Same shape as any guide (`guide_family: wing`), plus one extra section, and it is the only guide that carries it:

```markdown
## Current state
(3 to 5 lines: what this business is, what is moving right now. Written at the first capture,
refreshed at maintenance. This is what a session reads to know where things stand.)
```

Its door-sign line names the four layers in one sentence each: `01_Assets` what the business is made of · `02_Work` what is moving, in four lanes · `03_SOP` how things get done · `04_Methodology` why decisions go the way they go, and that this last one fills from reviewed judgment, never from capture.

Its **Files here when** test is the one that sorts the two wings: anything that is the business's rather than the owner's files on this side, and the object alone never decides it (a company van is `01_Assets/Equipment/`, the owner's car is `03_Personal-Wing/Vehicles/`). Nothing files at the wing root itself except `Business-Profile.md`.

The one directory of the vault: every folder that exists, plus its door file where it has one. Written at scaffold from the tree that was actually created (skip untoggled rooms, never list a path that does not exist), and audited against the filesystem at every maintenance run.

```markdown
updated: {{DATE}}
---

  (each with its own `_<Name>-Guide.md`)
```

Guide links are written **path-qualified** (§5, regime B): guide names repeat across wings by design, so a bare `[[_Run-Guide]]` is ambiguous the day a second business arrives.

⚠️ **Two lines in that skeleton are load-bearing for the `home-is-true` check and were each getting decided differently by different installs.**

- **The starter project line is written at step 6.95, not at step 5.** Step 5 writes Home from the tree it just created, and the starter project does not exist yet at that point; the step that creates it is the step that adds it (setup step 6.95, part A). ⛔ Do not write the line early: Home naming a folder that is not there yet fails the same check from the other direction, and an interrupted setup would leave it lying.
- **`99_Meta`'s three subfolders are named individually.** They used to be rolled into the word "templates, skills" inside one prose line, which reads as covered to one session and as missing to the next. Home is the only directory this vault has; a folder mentioned as a word in a sentence is not a folder that has been listed.

### `03_SOP/_SOP-Menu.md`

`03_SOP/` ships **empty and flat**: no starter processes, no category subfolders (§1). It ships with its door, and only its door.

The menu's shape is owned by the `sop-builder` skill, which reconciles this file against the folder every time it runs. ⛔ **Do not write a second version of it here.** Copy the template block verbatim from that skill's `references/sop-menu.md`, which at time of writing is:

```markdown
---
type: menu
updated: {{DATE}}
---

# SOP Menu

> Maintained by the SOP creation skill. Do not hand edit: the skill reconciles this file against the folder every time it runs, so hand edits get overwritten without warning.
>
> **What belongs in the second section**: processes that are **already happening but were never written down**. ⛔ Not processes that should exist one day. A wish list turns into a forty line guilt list in three months, and then nobody opens this file again.

## Written

## Happening but not written
```

Both sections ship **empty**. ⛔ Never pre-fill the second section with processes this kind of business usually has: the admission test is "is this already happening, and is it unwritten", and a list of things that ought to exist is a list of debts. That skill ships separately and the owner may not have it; a hand-written SOP is legal (§1, §7), and the menu is simply stale until either a skill run or the owner updates it.

### `01_Assets/{{BUSINESS}}-Brand-Assets/` (the brand rooms)

One `<Brand>-Brand-Assets/` folder per brand (§1). A single-brand business gets one, named after the business; capture asks which brand a thing belongs to only when a second brand exists.

Unlike other rooms (which scaffold empty and fill from capture), `Brand-Strategy/` and `Target-Audience/` are pre-populated at scaffold with **empty stub files**. The brand foundation is cross-cutting (every outward-facing piece of work reads it), so the schema exists from day zero; it just starts empty. Each stub is a **seed, not a blank**: its door sign names what it holds AND what stays broken while it is empty, so the gap is visible and worth filling. In Obsidian's graph these read as dim stars waiting to light up.

**The eight pillars are one family across two folders** (§1): seven in `Brand-Strategy/`, and the Journey pillar in `Target-Audience/`. All eight carry `type: brand-strategy` and a `pillar` value from the closed list in §8. The door signs below are canonical **English**; on a `中文` install, translate the door-sign prose at write time (file names stay English always).

**The seven stubs in `Brand-Strategy/`** (What + Empty cost per door sign):

- **Brand-Positioning.md** (pillar `Positioning`): What = "The place this business claims in the customer's mind, and who it is against." Empty cost = "every message starts from scratch and argues on the competitor's ground."
- **Brand-DNA.md** (pillar `DNA`): What = "What this business actually believes: the convictions behind its choices, not what it sells." Empty cost = "your marketing has no throughline. It reads like the category, never like you."
- **Brand-Personality.md** (pillar `Personality`): What = "The character the brand shows up as: how it talks, what it jokes about, what it would never say." Empty cost = "every post sounds written by a different stranger. Recognition needs one consistent voice."
- **Brand-Proposition.md** (pillar `Proposition`): What = "What you promise, and who the customer becomes by choosing you." Empty cost = "marketing can only list features. Features compete on price; promises get chosen."
- **Brand-Relationship.md** (pillar `Relationship`): What = "The role the brand plays in the customer's life, and how each touchpoint should feel." Empty cost = "service and follow-up get improvised. The feeling people remember is left to luck."
- **Brand-Sensory-Cues.md** (pillar `Sensory-Cues`): What = "The senses the brand chooses to own, so it's recognizable before anyone reads the name." Empty cost = "you default to the category's look and sound. Distinctiveness is chosen, not stumbled into."
- **Brand-Style.md** (pillar `Style`): What = "The concrete spec that renders those cues: color, type, logo use, spacing." Empty cost = "every designer and AI guesses. Consistency comes from one shared spec, not memory."

**`Target-Audience/Customer-Journey-Mapping.md`** (pillar `Journey`). Door sign: "The path one real person takes from never-heard-of-you to loyal, and how each stage should feel." Empty cost = "you market to a blur instead of a moment. The right message at the wrong stage still misses." ⚠️ It is the eighth pillar and carries the same `type: brand-strategy`, even though it files with the audience it maps; type comes from the family, never from the folder (§0 step 2).

**Stub file shape** (all eight): the `Brand-Pillar.md` block in [templates/note-templates.md](../templates/note-templates.md). Scaffold fills three things per stub and nothing else: the `pillar` value, the title, and the two prose lines above (the What line into the body, the empty-cost line into `**Empty cost:**`). `status: empty` and the closing "not defined yet" line come from the template unchanged, on all eight.

`status: empty` is the machine signal that this pillar has not been answered yet: any outward-facing work reads it to know it is running generic. The stub bodies name what is missing and its cost; they do **not** teach how to fill it (no frameworks, no course pitch): the vault stays clean, and the how-to lives outside it.

### `02_Command-Base/Command-Deck.html` (the dashboard, generated)

⛔ **Scaffold writes nothing here.** This file is produced by `scripts/deck.py build "<vault>"`, which setup runs once at step 6.95 and every session runs again at its start. There is no template to copy into the vault and no placeholder to leave behind: a dashboard file with nothing generating it is stale on day two and trusted on day one, which is why the earlier `.base` answer was retired rather than kept as a fallback.

Three properties the rest of this document depends on:

- **Zero hand-written state.** Every rebuild rewrites the whole file, so nothing on the page is authoritative about anything. That is what makes overwriting it safe without asking. A drag on the deck produces a proposed edit for a session to apply, never a write.
- **Zero config.** The deck re-derives the vault's shape on every run: wings from the top-level folders, lanes from the subfolders of `02_Work/`, brands from `<Brand>-Brand-Assets/`, interaction language from `bootstrap-progress.md`. A stored copy of any of those would be one more thing to keep true.
- **Atomic.** It writes a temp file and renames, so a failed rebuild leaves the previous deck standing with its own honest generation stamp. A stamp older than today makes the page say so and name the phrase that refreshes it.

**What it reads is entirely optional keys** (§8: `started`, `due`, `stage`, `priority`, `depends_on`, `hide_on_deck` on a Brief; `start`, `due`, `waiting_on` on a task). A project carrying none of them is perfectly legal, so the checker never mentions it and the frontmatter guard never stops it: it is simply a dark row. `scripts/deck.py doctor "<vault>"` is the only thing in the product that reports that, and it reports rather than repairs.

⚠️ **The `.base` dashboard this section used to describe is retired** (design ruling 2026-08-14, execution-backlog entry 46). Its template is gone from the payload, and no fallback copy was kept for a machine without `python3`: a second dashboard that can drift is worse than one dashboard that is honestly absent, and it would only serve owners who have Obsidian with the Bases plugin, who are not the same people as owners without Python. ⛔ **Neither the file nor its template is named literally anywhere in this payload any more, and that is on purpose**: a live-looking filename is what a future grep, and a future session, would read as something still in service. When `python3` is missing, setup records `deck: skipped-no-python`, says the dashboard is pending, and the fallback is `Home.md` plus the starter project's Brief, both of which are plain markdown.

### `03_Personal-Wing/Personal-Projects/Second-Brain-Rollout/` (the starter project)

Setup creates exactly one real project, in the personal wing, holding the work setup itself just left behind. It is not a demo and not a tutorial: every task in it is something the owner actually still has to do, which is the only reason it is allowed to exist. ⛔ Never seed a second one, and never invent a business project the owner has not mentioned.

It exists for two reasons that both fail without it. **Day one has no records**, so every panel on the deck would open empty and teach that the deck is a decoration. And **three other things already depend on a project being there**: the wiring check's `deck-is-alive` counts tasks against it, the deck's swimlane view needs one lane that is not empty, and the doctrine's "a task must have a project, there is no parking lot" rule needs somewhere for the owner's first task to go.

```markdown
started: {{DATE}}
due: {{DATE_PLUS_14}}
stage: executing
```

⚠️ **`started`, `due`, `priority` and `stage` are all optional keys in §8, and this is the one Brief that must carry every one of them.** The first day's Next Action, the Countdown cards and the swimlane bar are each derived from one of the four, so a Brief written by the product itself with them blank hands the owner a half-dark deck as their first impression and teaches, wordlessly, that frontmatter is decoration. `due` is fourteen days out; ⛔ do not invent a longer runway to look impressive.

`Tasks/` holds three notes from the Task template, `status: not-started`, `created: {{DATE}}`, each with a `due` so they land on the calendar. ⭐ **The file names are given here literally, not derived:**

1. `Give-your-AI-a-persona.md` (`due` +2 days): run Create-My-Jarvis, so the assistant stops being generic.
2. `Move-the-first-room-in.md` (`due` +6 days): the first capture session, starting with the Business Profile.
3. `Decide-on-the-optional-pieces.md` (`due` +13 days): the calendar connection and session memory, each a yes or a no.

The body of each is the sentence its name spells out, in the owner's language. Translate that sentence on a `中文` install; ⛔ **the three file names above stay exactly as written, on every install and in every language** (§4, law 6).

⚠️ **Why they are spelled out rather than left to be derived from a title.** §5 gives `YYYY-MM-DD-keyword-slug.md` for **dated records**, and nothing said whether a task is one, so one install wrote `Give-your-AI-a-persona.md` and another would have written `2026-08-18-give-ai-persona.md`, both reading the same law correctly. The rule that settles it for every task, not just these three, is in the Task template's own comment block (§5 delegates per-type naming there): **a task is not a dated record.** Its name is the task itself, hyphenated, Regime A; its dates live in `created:` and `due:`, and the day it was typed is not what anyone searches for.

### `99_Meta` state files

⛔ **None of the state files in this section carries a `type:` key, and that is the rule rather than an omission.** The line runs straight through the whole vault and is worth stating in one sentence, because a session that does not know it will add the key out of tidiness: **a file with `type:` is a document, something a person reads and §8 governs; a file without one is state, a machine's notepad.** `filing-log.md`, `bootstrap-progress.md`, `capture-progress.md`, `maintenance-state.md` and `capture-buffer.md` are all the second kind. Nobody reads them for content, no template exists for them to be an instance of, and setup writes each one exactly once.

⚠️ **The other four files in `99_Meta/` do carry `type:`, and the difference is not arbitrary.** The doctrine, the tag vocabulary, `lab-gate-config.md` and `profile.md` each ship from their own template, each template already carries `type:` in its frontmatter, and each is a document a person opens and reads. Those four are the whole of §8's `control` family. ⛔ **Do not add these state files to it**, and ⛔ do not add `type:` to them to "make the checker see them": the checker skips a file with no `type:` on purpose, so a correct install is silent about its own notepads, and a `type:` value §8 has never declared is exactly what makes it complain. Adding the key is what breaks the check, not what satisfies it. (Ruling 2026-08-16; before it, the spec said neither, and one install added the key and got three warnings on a correct house while another did not and passed.)

⭐ **Each of the three below ships with its shape written out as a block, and setup writes that block.** They are singletons: no template owns them, nothing else in the payload carries their shape, and a prose list of key names is not a shape. Two installs reading a prose list produce two different files, which is the whole reason the blocks are here.

`filing-log.md`:


## Wiring check (run after scaffold, before the graph moment)

⛔ **Refer to a check by its NAME, never by its number.** The bold name opening each line is the handle; the numbers are ordering only, and every insertion shifts the ones below it. This is not a style preference, it is the one failure this list has actually produced: it has been renumbered twice, and both times every document citing a number silently began pointing at a different check, with nothing raising (see the execution-backlog entries for the guards check and the deck check, which each named a number that by then belonged to something else). 1. **`one-door-per-folder`.** Every room, lane, brand subfolder and wing holds exactly one `_`-prefixed file; no folder holds two (§5). The four layer folders and `04_Methodology/` hold none.
2. **`home-is-true`.** Every folder created is listed in `Home.md`, and every folder path `Home.md` spells out exists on disk. This replaces the old "two hops to both wings" check: with a full directory, reachability is not the question, accuracy is.

    **What counts as listed, and what is deliberately not listed.** A folder is listed when its name appears in `Home.md`, whether as a path (`Personal-Projects/Second-Brain-Rollout/`) or as a name in one of the grouped lines (`Clippings`); Home is a directory a person reads, not a path dump. Exactly **two** classes of folder are exempt, and both are named here so nobody has to judge:

    - **Inside a project folder** (its `Tasks/`, and the closet folder beside a note that owns non-markdown files, §2). The project folder itself IS listed; what is inside it is the project's business, and its Brief is the address (doctrine §3, link once and derive the rest).

Home names `99_Meta/Skills/` and stops: a skill package's working address is `~/.claude/skills/<name>`, not a path in this vault, and the alternative is that every mode which generates a skill also has to remember to write a Home line.
